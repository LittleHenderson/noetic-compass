# Render → AWS lane migration

Written 2026-09-26. Companion to the accounts-off API move recorded in
`CHANGELOG.md` ("Public dashboard API moved from Render to AWS App Runner").

## Why this exists

Render suspended the whole workspace. Every service in it — the two API lanes, the
accounts-canary private service, and the `atlas-viewer-app` static site — answered HTTP
503 with the response header `x-render-routing: suspend`, while Render's own status page
reported all systems operational. The public dashboard's API was moved to AWS App Runner
on 2026-09-26 and the login page works again.

The remaining lanes have not moved. This document records exactly what is left, what
blocks it, and the order to do it in.

## Blockers

These are the reasons the two API lanes cannot be lifted and shifted today.

### 1. Render-held secrets are not in the repository

Both API lanes depend on values that exist only in Render's dashboard. `generateValue: true`
means Render created the value itself; `sync: false` means a human typed it in.

Generated by Render:

- `NC_ACCOUNT_CREDENTIAL_PEPPER` — **the hard one.** Stored account credentials are derived
  with this pepper. Replacing it locks every existing account out permanently.
  `render.customer.yaml` says so in its own words: deleting a declared `generateValue` key
  makes a later sync create a different value, and "that is a destructive rotation, not
  recovery."
- `NC_JWT_SECRET`, `NC_ACCOUNT_BOOTSTRAP_SECRET`,
  `NC_PLATFORM_TENANT_PROVISIONING_SECRET`, `NC_BILLING_ADMIN_SECRET`,
  `NC_EVIDENCE_SHARE_TOKEN_PEPPER`, `NC_OBJECT_LOCK_RECEIPT_ATTESTATION_KEY`.

Entered by hand (`sync: false`):

- `NC_HUMAN_ATTESTATION_PSEUDONYM_KEYRING_JSON` and its active key id,
  `NC_CUSTOMER_PRODUCTION_PSEUDONYM_KEYRING_JSON` and its active key id,
  `NC_AIRTABLE_TOKEN`, `NC_AIRTABLE_BASE_ID`, `NC_AIRTABLE_TABLE_NAME`,
  `NC_AIRTABLE_DEDUP_FIELD`, `NC_AIRTABLE_OWNER_FIELD`, `NC_AIRTABLE_OWNER_VALUE`,
  `NC_AIRTABLE_LIFECYCLE_FIELD`, `ATLAS_LIVE_WORKER_URL`, `ATLAS_LIVE_WORKER_TOKEN`,
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `CAS_HARNESS_EVIDENCE_ANCHOR_S3_BUCKET`.

All of these are readable through Render's REST API (`GET /v1/services/{id}/env-vars`) using
the `RENDER_API_KEY` already stored as a GitHub Actions secret in this repository. That key
still worked on 2026-09-26T00:54Z: the production monitor's blueprint job read live Render
service configuration successfully in that run.

Reading the values is necessary. Newly generated values are not an acceptable substitute for
`NC_ACCOUNT_CREDENTIAL_PEPPER` or for the attestation keyrings.

### 2. Data cannot be exported while the workspace is suspended

- **Postgres.** The customer database is declared network-isolated (`ipAllowList: []`, and
  `networkIsolationEnabled: true` on its environment), so it is reachable only from inside
  Render's private network. The production monitor reports that the live `ipAllowList` has
  drifted from the manifest, so the live posture needs readback rather than assumption. Either
  way there is no dump path from outside while the service that writes it is not running.
- **The support disk.** `/var/customer-support` holds the CRM and support JSONL migration
  sources and the file-backed Evidence Packet and hash-log surface. It lives inside the
  suspended service; there is no API to download it.
- `render.customer.yaml` states the disk "remains until every other file authority migrates
  and hosted parity is proven," so those files are still load-bearing.

Consequence: a lane moved today arrives **empty**. That is acceptable only if the lanes hold
test data only.

### 3. The repository's own controls pin production to Render

Migrating the customer lane is a governed change, not just an infrastructure change. These
files name Render identities and will fail CI or invalidate the release contract if left
stale:

- `.production/customer-production-acceptance.json` — pins the API origin
  `https://cas-harness-customer-api.onrender.com` and Render service
  `srv-d9bijbjtqb8s73cn4n20` as production authority. Its product status is `OPEN`
  ("Required customer-production evidence gates are not yet all present"), so the public
  product has not been accepted yet.
- `noetic-compass-scaffold/noetic-compass/docs/runbooks/customer_production_acceptance.md` —
  same pins, in prose.
- `.render/blueprint-control.json` plus `scripts/verify_render_blueprint_control.py` and its
  test — the `render-blueprint-control-offline` job is a **required status check** on
  `master`, so a migration that leaves these inconsistent cannot merge.
- `noetic-compass-scaffold/noetic-compass/atlas-viewer/render-route-rules.json` — records
  `requiredApiBaseUrl` as the customer API and `requiredAccountsEnabled: "true"`. The Atlas
  viewer therefore moves with the customer API, not before it.
- GitHub repository variable `CAS_PRODUCTION_API_BASE_URL`, currently
  `https://cas-harness-customer-api.onrender.com`.

## Cutover order, once unblocked

1. Restore access to Render so that secrets can be read and data can be exported.
2. Read every lane secret through the Render API and store it in AWS Secrets Manager or SSM
   Parameter Store as a SecureString. Never print a value and never commit one.
3. Dump each Postgres database and copy the `/var/customer-support` tree out.
4. Restore both into RDS and an EFS mount or S3 prefix, then prove hosted parity.
5. Build the canary branch image separately: `nc-api-image-build` currently builds `master`;
   the canary lane tracks `release/accounts-canary-20260713`.
6. Create the two App Runner services with the recovered secrets and the same database URLs.
7. Update the control plane in one reviewable pull request: acceptance contract, runbook,
   `.render/blueprint-control.json`, the verifier and its tests, `render-route-rules.json`,
   and the `CAS_PRODUCTION_API_BASE_URL` repository variable.
8. Move the Atlas viewer to S3 + CloudFront with the new API base URL, then re-run the
   customer-production acceptance gates.
9. Only then retire the Render lanes.

## Rollback

Until step 9, Render remains the declared production authority. Steps 1–6 are additive: they
create AWS resources that serve nothing until a control-plane change points at them. The
accounts-off lane is already cut over and can be rolled back by reverting the `vercel.json`
rewrite to the Render URL in one commit.

### Constraint discovered: the production identity is one tuple

`scripts/tests/test_acceptance_authority_contract_alignment.py` pins the production identity
as a single tuple — API origin, Render service id `srv-d9bijbjtqb8s73cn4n20`, service name,
Render disk id `dsk-d9bijbjtqb8s73cn4o60`, and the root-CI deploy identity — and asserts that
roughly ten modules agree on it: the authority contract constant, the runtime verifier, the
readiness collector, the alert builder, the CRM, journey and operational collectors, the
root-CI collector, the Render blueprint verifier, and the Atlas route contract.

Consequence: **the origin cannot move to AWS while the Render identity remains.** Rewriting the
files that name the Render API host fails that test, because the Render blueprint verifier must
keep expecting Render's own service URL for its live check to pass.

So the hostname sweep and the retirement of the Render identity are the *same* change, not two.
That reorders the plan: Render cannot be retired strictly last. Either the Render identity for
the migrated lanes is retired together with the sweep, or the declared origin stays on Render
until it is.

The sweep itself is scripted and ready: `scripts/plan_render_hostname_sweep.py` reports 38
files and 52 occurrences to rewrite, and five files to leave alone with a stated reason
(historical records, the Render blueprints, the hand-edited runbook, and the two Render control
scripts that grep *for* the Render host on purpose). It defaults to a dry run.
