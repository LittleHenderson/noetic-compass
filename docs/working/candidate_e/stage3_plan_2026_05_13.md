E2c-continuation answered: **"Can the model copy the right source ID when the correct sentence context is given?"** → Yes (TF per-token 0.923 on fresh dev records).

## 3. Stage 3 mechanism options

### Option A — Scheduled sampling (curriculum from TF → free-decode mix)

**Mechanism:** during training, the decoder input at each step is a probabilistic mix of (gold next token) and (model's own argmax from previous step). Start probability of using model output `p_self` = 0.0 (pure TF, same as E2c). Linearly anneal `p_self` → 0.5 (or 1.0) across training steps.

**Pros:**
- Minimal new code: hook into the decoder loop, swap teacher-forced input for argmax at each step with probability `p_self`.
- Same losses (L_lm + L_copy + L_span + L_contrastive + L_coverage + L_start_anchor + L_anchor_contrastive). No new loss design.
- Curriculum naturally bridges TF and free-decode.

**Cons:**
- The model still trains on gold targets. When the prefix drifts (due to scheduled sampling), the gold target for that token may not match what a correct continuation would be. Some loss-signal noise.
- Doesn't generate fresh trajectories; learns on existing corpus with model-prefix-mix.

### Option B — DAgger (Dataset Aggregation)

**Mechanism:** model free-decodes record-by-record. For each STAGE_VAR span position where argmax differs from gold src, record the (state, gold_action) correction. Aggregate corrections into a supplementary training set. Retrain with mixed (original + corrections) data. Iterate.

**Pros:**
- Directly addresses free-decode distribution shift. Generates trajectories in the actual deployment distribution.
- Cleaner theoretical grounding for the question Stage 3 asks.

**Cons:**
- Heavier infrastructure: rollout loop + correction collector + training-set augmentation. ~3-5× the code surface of scheduled sampling.
- Multiple training iterations. Compute cost higher.
- Risk of the "DAgger on a model that hasn't learned binding under TF" failure mode that Codex flagged in the original design doc. We're past that bar now (0.923 TF), so this risk is lower.

### Option C — Hybrid (scheduled sampling first, DAgger only if needed)

Run scheduled sampling first as the lighter intervention. If post-training free-decode gate misses, then design DAgger. Don't over-build until evidence demands it.

## 4. Recommendation

**Option C, with the pre-Stage-3 measurement first** (§2).

Reasoning:
- The simplest intervention (scheduled sampling) is also the smallest reversible step. Codex's audit pattern is "lighter intervention first, design heavier loss only on evidence of need" — same logic that worked for E2c continuation vs body-digit drift loss.
- The pre-Stage-3 free-decode baseline is cheap and tells us whether the intervention even needs to be aggressive.
- If E2c continuation already free-decodes at, say, 0.50+ identifier recovery, scheduled sampling with mild `p_self` annealing may be enough. If it's 0% (A/B/C/D pattern), more aggressive curriculum or DAgger is on the table.

## 5. Locked Stage 3 gates (PLAIN VERSION, post-Codex-Findings 2 & 3)

**The load-bearing question:** does the model produce the SOURCE'S body digits in free-decode, not memorized or hallucinated body digits?

### Two-tier free-decode gate (Codex Finding 2)

- **First pass (Stage 3 minimum bar):** dev `identifier_recovery_rate` under free-decode ≥ **0.50**. Says the behavior survived generation enough to be real.
- **Strong pass:** dev free-decode `identifier_recovery_rate` ≥ **0.70**. Says the behavior is becoming usable.
- **Kill / redesign:** post-training stays below **0.30**. Scheduled sampling did not solve the exposure problem; move to DAgger or different intervention design. **Do not retry scheduled sampling with different hparams (anti-tuning).**

Reasoning:
- E2b free-decode `identifier_recovery_rate` was 0.31 (TF 0.006).
- E2c-continuation TF is 0.923; free-decode unknown until baseline (§2).
- 0.50 ≈ half the TF capability and clearly above the old failed behavior. Stage 3 minimum.
- 0.70 = strong pass. Not 0.923 — free-decode is strictly harder than TF.
- 0.30 floor = no measurable improvement over E2b's already-known free-decode (E2b 0.31).

### Hard safety gate (Codex Finding 3)

- **`swap_summary.cross_emission_count == 0` is HARD.** Non-zero = the model is emitting the OTHER pair member's source body in its output → memorization / leakage signature. Stage 3 cannot pass with non-zero cross-emission, even if `identifier_recovery_rate` clears 0.50.
- `pair_pass_rate >= 0.50` is diagnostic / strong-signal only. Not a hard gate.

This avoids passing a model that leaks the other pair member's ID while still not over-fitting the whole run to strict pair pass.

## 6b. Scheduled sampling implementation requirements (Codex Finding 6, SHARPENED)

The original draft's "minimal new code, hook into the decoder loop" was too optimistic. The current trainer is batched/teacher-forced — there is no naturally sequential decode loop in training. Real requirements:

### Variant choice (refreshed 2026-05-13T05:54Z)

Per Codex re-audit: this implementation is the Bengio et al. (2015) **one-step (TF-conditioned)** variant of scheduled sampling. It is NOT a fully autoregressive student rollout.

- **What the cheap variant does (implemented):** one no-grad forward at the gold prefix produces "what would the model predict next" tokens at every position; those tokens are mixed into the decoder input via per-position Bernoulli; then one with-grad forward at the mixed prefix produces loss against gold. 2 forwards/step.
- **What the full variant would do (NOT implemented):** L no-grad forwards, each conditioning on the prior already-substituted prefix. Models the true free-decode distribution at the cost of ~L× compute.
- **Why cheap first:** 2 vs L forwards per step; this is the standard published variant (T5, NMT); if it fails to close the TF→free-decode gap the full rollout upgrade is a strict superset, nothing has to be unwound.

### Functional requirements (as built)

1. **Two-pass construction.** For each training step:
   - Pass 1 (no-grad): `model(batch)` at gold prefix → greedy argmax over `lm_logits` → shift-right → "previous-position sampled token" candidates. One forward, `torch.no_grad()`.
   - Mix: per-position Bernoulli(ratio) random mask. Position 0 (BOS) hard-fixed to gold.
   - Pass 2 (with grad): `model(mixed_batch)` against gold targets. Backprop only through pass 2.

2. **NO backprop through sampled argmax tokens.** They enter pass 2 as discrete integer inputs. Gradient flow is identical in shape to E2c, just with a different (mixed-gold-and-model) decoder input prefix.

3. **Target alignment preserved.** Gold targets stay the same; only the decoder input sequence changes. The loss expects "next token given prefix" — when prefix is mixed, the gold answer for "what comes next at THIS position" is unchanged from the corpus.

4. **Ratio schedule plumbed through.** `resolve_ratio_at_step(schedule, constant_ratio, step, n_steps)` returns the per-step ratio. Supported: constant (`--scheduled-sampling-ratio`) and `linear:<start>-<end>:<warmup>-<full>` (`--scheduled-sampling-schedule`). Schedule wins when both set.

5. **Position-independent sampling decision.** Bernoulli draw with the per-step ratio, independent across positions. BOS never substituted regardless of ratio.

### Tests (as landed)

23 tests in `tests/training/test_scheduled_sampling.py`. Three load-bearing groups:

- **Equivalence at ratio=0.** `test_forward_at_ratio_zero_returns_identical_outputs` + `test_forward_at_ratio_zero_gradients_match_tf` + `test_forward_at_ratio_zero_loss_matches_tf`. Uses `torch.equal` (no `allclose`) on every output tensor and every per-parameter gradient. (Earlier draft of this plan said "byte-identical" — the actual claim is bit-for-bit-equal tensor + gradient values via `torch.equal`, which is stronger than "byte-identical" for the same memory layout but weaker if either tensor is rematerialized through a no-op transform. The `torch.equal` form is what we pin.)
- **Self-feed at ratio=1.** `test_forward_at_ratio_one_self_feed_runs_end_to_end` + `test_forward_at_ratio_one_gradients_nonzero` + `test_forward_at_ratio_one_changes_outputs_vs_tf`.
- **Direct mixed_input inspection (Codex re-audit blocker 2).** `test_build_input_at_ratio_one_substitutes_every_non_bos_position` + `test_build_input_never_substitutes_bos_at_any_ratio` (across ratios 0.1/0.5/0.9/1.0) + `test_build_input_at_middle_ratio_mixes_gold_and_sampled` + `test_build_input_at_ratio_zero_does_not_substitute`. These look at the actual `mixed_input`, `use_sample`, `sampled_prev` tensors returned by `build_scheduled_sampling_input` rather than inferring substitution from output divergence.

### Implementation surface (as built)

- New module: `cas_native/training/scheduled_sampling.py` (commit `dd07bdb`). Two public helpers: `forward_with_scheduled_sampling` (top-level entry) and `build_scheduled_sampling_input` (factored substitution-mask builder, exposed for direct testing). Plus `resolve_ratio_at_step`.
- Hook into `train_simplex_mvp.py` training loop: per-step `ss_ratio = resolve_ratio_at_step(...)`; if `ss_ratio > 0.0` dispatch through `forward_with_scheduled_sampling`, else `model(batch)` unchanged.
- 23 tests in `tests/training/test_scheduled_sampling.py`.
- `train_progress` event gains a `scheduled_sampling_ratio` field (per-step) for observability.
